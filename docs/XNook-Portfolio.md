## 三、三个可展开的技术亮点

这部分是申请材料里最值钱的内容——**不是「我做了什么功能」，而是「我遇到了什么真问题、怎么定位、怎么解决」**。港校导师看的是这个。

### 亮点 1：Liquid Glass 材质的对比度缺陷定位（最推荐）

**问题**：macOS 26 的 `.glassEffect` 材质在深色模式（白字）叠加浅色壁纸时，文字对比度降到 **1.11:1**（WCAG AA 要求 4.5:1），几乎不可读。

**过程**：

1. 最初用离屏渲染（`NSHostingView + cacheDisplay`）验证，得出「玻璃面板轮廓消失」的结论；
2. **发现该结论错误并主动推翻**——探针脚本输入的背景是深灰 `Color(white: 0.12)`，但离屏输出是全谱彩虹渐变，与输入不符；
3. 定位根因：`.glassEffect` 依赖窗口合成器采样「视图背后」的内容，离屏渲染走不到这条路径，产出的是未定义内容；
4. 改用真实窗口 + `screencapture -R` 抓屏，并解决两个坑（`NSWindow` 左下角原点 vs `screencapture` 左上角原点；必须用两个独立窗口模拟生产环境的采样路径）；
5. 实测出根因：**玻璃对背景的响应是「压暗」**，且深浅模式不对称——深色模式下黑色背衬可把对比度拉到 8.94:1，浅色模式下白色背衬即使加到 92% 也只有 3.11:1；
6. 最终决策：玻璃仅在深色模式启用，浅色模式回退纯色；背衬不透明度收敛到 `IslandGlassTuning`，并用测试锁住 0.45 安全下限。

**为什么这段值钱**：它展示了一个完整的科研式闭环——**提出假设 → 验证 → 发现验证方法本身有缺陷 → 修正方法 → 得到可靠结论 → 用工程手段固化**。其中「主动推翻自己的结论」这一点，比结论本身更能说明问题。

证据：`docs/verification/liquid-glass-contrast.md`（含实测数据表与三张对比图）

### 亮点 2：数据可靠性的系统性加固

**问题**：审查发现 5 类 P1 级数据丢失风险，其中最关键的是——**读取失败被误判为「首次启动」，随后立即保存，导致仍有恢复价值的原文件被示例数据覆盖**。

**处理**：区分「文件不存在」与「读取失败」两种状态；读取失败时保留原件并进入保护状态，提供备份恢复入口；保存失败保留草稿；退出时默认不放弃未保存内容。

同类问题还包括：离线外接盘的文件引用被后续保存永久抹掉（改为跨保存保留未解析记录）、损坏的 NookFlow 历史被新任务覆盖（改为错误状态 + 禁止写回）。

**为什么这段值钱**：它体现的是**对「失败路径」的设计意识**——不是功能能跑通就行，而是异常发生时数据不丢。这是工程成熟度的直接证据。

证据：`docs/reviews/2026-10-18-macos-runtime-and-optimization.md` 第 3 节

### 亮点 3：跨平台移植与算法终止性验证

**问题**：Windows 客户端解析 ICS 日历文件时，一个不超过 5 MiB 的文件可以包含大量主事件，每个事件独立扫描全表并各自拥有展开预算，累积结果无总上限；更严重的是，**不可满足的 DAILY 日期组合能让依赖内部搜索不返回**，外部 25000 次计数无法抢占。

**处理**：把整个解析、验证、迭代器初始化和展开放入可终止 Worker；主线程设截止时间执行 terminate；导入/刷新失败时保留旧数据。复现记录：正常规则约 0.299 秒返回两项；不可满足规则在外部 2 秒期限内未返回，由受控子进程终止，无残留进程。

**为什么这段值钱**：这是**算法层面的终止性（termination）问题**，不是普通的性能优化。能识别出「外部计数无法抢占同步死循环」这一点，说明对并发模型有实际理解。这段在 PhD 面试里可以作为「我处理过一个终止性不可判定场景」的例子展开。

证据：`docs/reviews/2026-10-18-macos-runtime-and-optimization.md` 第 5 节

## 四、申请材料中的使用建议

### 放在哪里

| 材料 | 用法 |
|---|---|
| **CV / 简历** | 项目经历栏，用第一节的一句话定位 + 第二组量化数字（挑 3–4 个） |
| **PS / SoP** | 不要整段写功能。选**一个**技术亮点（推荐亮点 1）展开成「我如何思考一个技术问题」的叙事 |
| **面试** | 三个亮点都可以讲，优先亮点 1 和 3 |
| **推荐信素材** | 如果找导师写推荐信，把这份材料发给他，让他能写出具体细节而不是空泛评价 |

### 不要写什么

- 不要写「功能丰富」「用户体验好」这类无证据的形容；
- 不要把 14 个版本说成「14 次重大迭代」——实际是 14 个发布版本，措辞要准确；
- 不要声称「411 项测试全部通过」而不标注日期——审阅者可能追问，写清「2026-10-23 实测」更可信；
- 不要把「软著申请」写成「已获得软著」——需先确认当前状态。

### 一个关键提醒

这份材料里**最有说服力的不是代码量，而是那份 `docs/verification/` 下的验证记录**。它证明你有「先测量、再下结论」的习惯，并且会记录负面结果（「该结论错误，已推翻」）。这在 PhD 申请里是**稀缺信号**——大多数本科生项目只能展示「我做出了什么」，你能展示「我如何知道自己做对了」。

如果要在 PS 里只留一句话，我建议是：

> 在定位一个 macOS 玻璃材质的可读性缺陷时，我发现最初的离屏渲染验证方法本身会产生伪影，于是推翻了基于它的结论，改用真实窗口抓屏重新测量，最终得到与初判相反的根因。
