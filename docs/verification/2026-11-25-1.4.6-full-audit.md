## 三、缺陷详情

### （一）P0-1：实时字幕调度器非法区间导致应用闪退

**现象**

已安装的 1.4.6 在 2026-11-22 14:45:26 发生一次真实崩溃：`EXC_BREAKPOINT / SIGTRAP`，主线程报 `Swift runtime failure: Range requires lowerBound <= upperBound`。崩溃进程于 2026-11-21 21:25 启动，运行约 17 小时后退出。

**证据**

1. 崩溃报告：`~/Library/Logs/DiagnosticReports/X Nook-2026-11-22-144526.ips`。
2. 故障栈：`CaptionScheduler.coverageRatio(of:in:)` → `CaptionScheduler.refreshCertificate(unitIndex:now:)` → `CaptionScheduler.ingest(_:)`。
3. 精确位置：`Sources/XNook/Features/Caption/CaptionScheduler.swift:293`：

```swift
max($0.start, bounds.lowerBound)..<min($0.end, bounds.upperBound)
```

4. 临时探针（已删除）用候选 `start = -1.5, end = -0.5` 调用 `scheduler.ingest([candidate])`，稳定复现：

```text
Fatal error: Range requires lowerBound <= upperBound
error: Process ... exited with unexpected signal code 5
```

**根因**

`coverageRatio` 假设“候选与区间必有交集”，但只过滤了 `end > readBoundary`。当候选整段落在 0 号区间之前（负时间戳）时：

```text
bounds = 0..<2
lower = max(-1.5, 0) = 0
upper = min(-0.5, 2) = -0.5
0..<(-0.5)  // precondition failure
```

负时间戳的生产路径是“跨时间轴重置的迟到 OCR”：

1. `CaptionManager.start()` 或播放器时间轴不稳定时会调用 `clock.resetToZero()`（`CaptionManager.swift:106`、`:321`）。
2. `FrameTextEvidenceProvider.reset()` 只清 `lastRequestedInterval` 和 `lastText`，**不会作废正在执行的 OCR**（`FrameTextEvidenceProvider.swift:67-70`）。
3. OCR 完成时用 `clock.sourceTime(atHost: captureHost)` 计算时间；`captureHost` 早于新锚点，得到负 `start`（`:147`）。
4. 候选代次取的是**完成时**的 `clock.generation`，不是抓帧时的代次（`:166`），因此新代次检查无法丢弃它。
5. 候选进入 0 号桶，触发上述非法区间。

**影响**

应用直接终止，用户正在看的字幕、面板状态全部丢失；这是“开启实时字幕并经历 seek/时间轴重建”场景下的随机闪退，复现概率随使用时长上升。

**修复建议**

1. `coverageRatio` 先求交再判空，禁止直接构造可能倒置的 Range：

```swift
let lower = max(candidate.start, bounds.lowerBound)
let upper = min(candidate.end, bounds.upperBound)
guard lower < upper else { continue }
intervals.append(lower..<upper)
```

2. `FrameTextEvidenceProvider` 在抓帧时捕获代次，完成时代次不一致直接丢弃；或让 `reset()` 递增内部 epoch 并使在途任务失效。
3. 在 `ingest` 入口拒绝 `end <= 0` 或对负时间戳钳制到 0，作为第二道防线。
4. 增加回归测试：负时间戳候选、跨 `resetToZero` 的迟到 OCR、空交集候选、NaN 时间戳。

### （二）P1-1：暂停后残留字幕让胶囊持续滚动，空闲 CPU 约 19%

**现象**

音乐在 10:28 暂停后，到 11:00 胶囊仍保持 60pt 高（无 Ticker 时为 41pt），并持续横向滚动最后一句字幕（截图可见），没有回到静态收起态。

**证据**

1. 运行中采样：`top -l 2 -pid <pid>` 空闲 CPU 16.1%–19.4%，RSS 135 MB。
2. 可逆 A/B：

| 条件 | CPU |
|---|---:|
| 实时字幕开 + 残留字幕滚动 | 19.4% |
| 实时字幕关 | 0.5% |
| 实时字幕开 + 减弱动态效果 | 6.0%（此前同条件 16.1%） |

3. 5 秒 `sample` 显示主线程大量时间在 `UpdateCycle`，栈中出现 `MarqueeText` 的 `TimelineView(.animation)` 与文本重建。
4. 胶囊窗口从 271×41 变为 271×60，恰好是 Ticker 行的高度差。
5. `caption.log` 显示 10:28:45 暂停后该字幕行持续保留；`session locale=en-US` 累计 4894 次，说明字幕会话长期运行。

**根因**

1. 暂停时 `SourceClock.freeze()` 冻结时间轴，`CaptionManager.expireCaptionLineIfNeeded()` 的 `now` 不再前进，最后一行字幕永不超时清除——这本身是 1.4.6 有意为之的“暂停画面定格”。
2. 但 `NotchContentView.showTicker` 对 `captionLineActive` 无条件返回 `true`，不检查 `mediaManager.isPlaying`（`NotchContentView.swift:235-240`）。
3. `tickerText` 又把 `captionManager.line` 作为第 4 优先级返回（`:1699`）。
4. `MarqueeText` 在文字超宽时使用 `TimelineView(.animation)`，跟随屏幕刷新率逐帧重建；ProMotion 下相当于持续 120fps 重绘一行滚动文本（`MarqueeText.swift:19-23`）。

**影响**

一个应当“安静待机”的菜单栏工具在暂停状态下持续占用约 1/5 个核心，造成耗电、发热和风扇噪音；同时用户看到的是“已暂停但字幕还在动”的矛盾状态。

**修复建议**

1. 暂停时停止 Ticker 动画：`isAnimated` 传入 `mediaManager.isPlaying || mediaManager.isWaitingForPreferredSource`；或给 `MarqueeText` 增加 `isPaused`。
2. 若希望保留“定格字幕”，把 `showTicker` 的 `captionLineActive` 分支也加上 `mediaManager.isPlaying` 条件，只保留静态文本或不显示 Ticker。
3. 将 `TimelineView(.animation)` 降为 30fps 的 `.periodic`，避免 ProMotion 级别的无意义重绘。
4. 无音频输入一段时间后自动挂起 SCK/语音会话（例如 60–120 秒静音），而不是持续建会话。
5. 增加能耗回归：实时字幕开启且暂停 60 秒，空闲 CPU 应低于 2%。

### （三）P1-2：`overviewPage` 多视图被 ZStack 压在同一坐标

**现象**

1. 当用户隐藏“当前任务”和“最近任务”两个模块、且 `showTaskInboxShortcut` 为真（默认值）时，待办入口按钮与组件网格出现在同一位置，压在笔记卡片上。
2. 当布局文件损坏或布局加载异常时，错误提示和“恢复默认布局”按钮也会盖在网格上。
3. 无 `PanelLayoutStore` 的旧回退布局中，组件网格与任务区 100% 重叠。

**证据**

1. `TaskInboxShortcutVisibilityTests` 启用渲染后：1 个用例、8 个断言失败。记录显示 `panelTaskInboxFallback` 的 `y=49`，而笔记卡片的范围是 `169..223`；关闭入口开关后内容高度变化为 0，说明入口根本没有参与布局。
2. `AdaptiveWorkflowPreviewTests` 启用渲染后：16 个用例、202 个断言失败。记录显示任务区 `y=49 h=162` 与组件区 `y=49 h=186` 完全重叠。
3. 证据图 `.build/compact-panel-evidence/ui/widget-matrix-800-mask-11.png` 可见任务区盖住组件卡片、底部卡片被裁切。

**根因**

`ExpandedPanelView.overviewPage` 是 `@ViewBuilder`，在 `layoutStore == nil` 分支返回 `overview` + `focusContent` 两个兄弟视图；在 `layoutStore != nil` 分支可能返回“错误文本 + 恢复按钮 + 网格 + 待办入口”多个兄弟视图。它被直接放入：

```swift
ZStack(alignment: .topLeading) {
    if selectedWidget == nil { overviewPage }
    ...
}
```

SwiftUI 会把 `TupleView` 的多个子视图当作 ZStack 的多个子节点，而不是垂直堆叠，于是全部落在同一原点（`ExpandedPanelView.swift:146-148`、`:417-456`）。

**影响**

生产默认布局（任务模块可见）不受影响，生产仪表盘渲染图与 `PanelGridNativeTests` 均正常；但只要用户隐藏两个任务模块（受支持配置），待办入口就不可用且遮挡内容；布局损坏时恢复入口也会被盖住。旧回退路径完全不可用，相关 13 个布局测试因此全红。

**修复建议**

1. 在 `overviewPage` 内部用单一容器包住所有兄弟视图，例如 `VStack(alignment: .leading, spacing: 8) { ... }`，让 ZStack 只看到一个子视图。
2. 布局错误提示、恢复按钮和待办入口都放入同一个 VStack，保持正常占位。
3. 把渲染验收测试纳入默认 CI（至少发布前必跑），否则该回归会继续被“跳过”掩盖。
4. 增加“隐藏任务模块 + 待办入口”与“损坏布局恢复”两个真实生产布局的回归快照。

### （四）P2-1：`caption.log` 无限增长且保存完整转写内容

**现象**

`~/Library/Logs/XNook/caption.log` 已达 4.96 MB、约 7.3 万行，8 天未轮转；每 10 秒写 `pretranscript: tick file=nil 已转写至=0.0s`，每 30 秒写 `tap audio ... received`，并保存完整的 `line[...]` 转写文本。

**影响**

1. 长期运行会持续占用磁盘（按当前速率约数百 MB/年）。
2. 系统音频转写文本（可能包含会议、私人播放内容）长期明文留盘，并会进入 Time Machine/支持包；虽然父目录权限为 700，仍不符合“最小留存”原则。
3. 高频无效日志掩盖真正有用的诊断信息。

**修复建议**

1. 滚动日志：单文件 2–5 MB，保留 2–3 份；启动时截断或按天切分。
2. 默认不记录转写正文，只记录长度、哈希或区间号；需要排障时显式开启 debug 级别。
3. 合并 `pretranscript file=nil` 心跳，静音时停止输出。
4. 新建日志文件时设置 0600。

### （五）P2-2：ScreenCaptureKit 每秒丢帧 + MediaRemote 错误日志刷屏

**现象**

15 分钟内系统统一日志记录 5813 条 X Nook 日志，其中：

| 消息 | 次数/15 分钟 | 估算/天 |
|---|---:|---:|
| `stream output NOT found. Dropping frame.` | 899 | ≈ 8.6 万 |
| MediaRemote `Code=35` 一类错误 | 约 700 | ≈ 6.7 万 |

**根因**

1. `SystemAudioTap` 只添加 `.audio` 输出，却仍配置了 2×2、1fps 的视频流；SCK 仍生成视频帧，但找不到 `.screen` 输出，于是每秒丢弃并打日志（`SystemAudioTap.swift:94-107`）。
2. `MediaManager.start()` 无条件调用 `MediaRemoteBridge.registerForNotifications()`；但应用是本地自签名，直接读取 MediaRemote 返回空，实际信息走 Perl 桥。注册调用仍周期性触发 `MRMediaRemoteGetNowPlayingInfo` 错误。

**修复建议**

1. 给 SCStream 添加一个丢弃用的 `.screen` 输出（空 handler），或确认可用的“仅音频”配置，避免每秒 dropped-frame。
2. 在 `PerlMediaRemote.isAvailable` 为真时跳过 MediaRemote 通知注册；或按代码签名能力判断，自签名构建直接走 Perl 轮询。
3. 信息轮询从 1 秒放宽到 2–3 秒，或在面板收起且无歌词时降频；播放控制仍可即时执行。
4. 对日志数量加预算断言，超过阈值即失败。

### （六）P3-1：字幕会话每 50 秒重建，`SFSpeechRecognizer` 持续累积

**证据**

1. `leaks <pid>`：3020 个泄漏对象、136 KB，其中 124 个 `SFSpeechRecognizer` 相关节点。
2. `caption.log` 中 `session locale=en-US` 累计 4894 次；`SpeechEvidenceProvider.sessionLimit = 50`。
3. 当前 RSS 135–167 MB，2 分钟内保持稳定；泄漏量不大，但会话创建频率很高。

**分析**

`SpeechEvidenceProvider` 每次换会话都新建 `SFSpeechRecognizer`，而不是复用同一 locale 的 recognizer；系统框架对反复创建的 recognizer 保留内部状态，形成可观察的对象累积。虽非致命，但在常开字幕场景下是持续的无谓分配。

**修复建议**

按 locale 缓存并复用 `SFSpeechRecognizer`，只新建 `SFSpeechAudioBufferRecognitionRequest` 与 task；语言变化时再替换 recognizer。会话切换时显式 `endAudio()`、`cancel()` 并置空旧引用，配合泄漏回归。

### （七）P3-2：Swift 6 并发隔离警告

**证据**

Debug/Release 构建均有 4 条同一类警告（2 个唯一警告重复出现）：

```text
FrameTextEvidenceProvider.swift:13: conformance ... crosses into main actor-isolated code and can cause data races; this is an error in the Swift 6 language mode
PreTranscriptProvider.swift:14: 同上
```

`Sources/XNook` 中另有 17 处 `@unchecked Sendable`。

**影响**

当前协议方法都在主线程调用，未观察到实际竞态；但一旦升级 Swift 6 语言模式会直接编译失败，且未来若从后台队列调用 `start/stop` 会触发运行时隔离断言。

**修复建议**

统一 `CaptionEvidenceProvider` 的隔离域：要么把协议标记为 `@MainActor`，要么把 `start/stop` 保持 nonisolated 并用锁保护内部状态；逐项清理 `@unchecked Sendable`，至少为字幕调度器加并发注释与 TSan 测试。

### （八）P3-3：应用数据目录不一致

**证据**

- 笔记/托盘/GIF：`~/Library/Application Support/XNook`

**影响**

备份、迁移、支持排查时容易漏掉授权数据；同一产品的两个目录名也会让用户困惑。

**修复建议**

统一为一个目录（建议带空格的显示名 `X Nook`，或全用 `XNook`），首次启动做一次幂等迁移；导出逻辑显式说明是否包含授权凭据（默认不应包含密钥）。
