# XNook 当前版本评估与优化路线

日期：2026-10-18（Asia/Shanghai）。本报告覆盖产品体验、可靠性、性能、功能闭环和发布工程；安全结论引用独立生成的安全报告。

## 1. 结论

XNook 的定位和紧凑主界面已经成立：媒体、日历、文件托盘可以在小面积里完成查看与轻操作。下一阶段应优先保证数据不丢、异常输入不拖死界面、版本与测试证据一致，再扩展功能。

当前最重要的差距是：**正式版仍缺少工作区已有的数据保护；多个聊天直接修改同一个目录，使补丁与验收结果互相干扰；一些“管理器已实现”的能力没有形成可靠的用户操作闭环。**

建议保留用户刚恢复的原有面板和 200 高度上限。不要为了交付数据修复，再把未完成的新面板整体装回去。

## 3. 最先解决的数据可靠性问题

下表的 P1 是产品修复优先级；它不同于安全报告按攻击条件评定的严重度。

| 优先级 | 正式版 v1.3.17 中的风险 | 触发条件与影响 | 工作区状态 / 下一步 |
| --- | --- | --- | --- |
| P1 | 损坏笔记可能被示例笔记覆盖 | 读取或解码失败被当作首次启动，随后立即保存；可能覆盖仍有恢复价值的原文件 | 工作区已区分“不存在”和“读取失败”，提供保护及备份恢复；需独立交付 |
| P1 | 最近编辑可能丢失 | 500ms 延迟期间退出，或切换笔记后新编辑取消旧任务；正式版关闭与退出缺少完整 flush | 工作区已有立即更新内存、关闭/退出保存和失败阻止退出；需结合旧面板验收 |
| P1 | 离线文件引用被后续保存删除 | 外接盘离线启动后再增删其他文件，只保存可解析条目，离线引用被永久抹掉 | 工作区已跨保存保留未解析记录；需验证外接盘离线/重连 |
| P1 | 损坏 NookFlow 历史被新任务覆盖 | 解码失败后以空状态继续使用，下一次持久化覆盖旧数据 | 工作区已有错误状态与禁止写回；需独立发布 |
| P1 | 开发包与正式包可能并发写同一数据 | `.build` 包使用不同实例锁，但笔记、文件架、GIF 等默认目录相同；运行两个版本不能被视为数据隔离 | 应按数据目录共享单写锁，或为开发实例提供完整独立数据根；不自动迁移用户数据 |

正式版证据锚点：`NotesManager.swift:55–65、93–102、118–120`，`TrayManager.swift:74、240–248`，`FocusSessionManager.swift:109–112`，`SingleInstanceLock.swift:38–46`。这些位置指 **v1.3.17 标签**；当前工作区相同文件已经含有不同实现。

验收应使用临时数据：损坏 JSON、无写权限、快速连续编辑、关闭/退出、离线书签，再核对原件内容及备份。不要通过破坏用户真实数据做测试。

191.7ms 来自指定规模的隔离基准，不能推断为用户日常平均卡顿。本机运行进程一次读数约为 CPU 0.7%、RSS 47.6MiB；单次读数不足以证明长时间能耗和峰值表现。

## 5. 安全问题与修复状态

[Codex Security 自动生成的安全报告](/Users/meteor/.codex/state/plugins/codex-security/scans/XNook/299a5e79fc12228b1286dec2539af05c6343b364_20261017T183331Z_f_h04lka/report.md)是安全结果的主入口，包含威胁模型、证据和覆盖限制。

| 问题 | 前提与影响 | 必须完成的修复 |
| --- | --- | --- |
| macOS GIF 无资源预算（CWE-400） | 用户导入外部 GIF 后，整文件读取、缩略图及播放解码缺少统一尺寸/帧数预算，重新加载可能复发 | 普通文件有界读取；格式、画布、帧数、累计像素限制；缩略图、播放、旧文件及书签路径全部共用；失败不改原选择 |
| Windows ICS 总量放大（CWE-400/407） | 文件虽不超过 5MiB，却可包含大量主事件；每个事件扫描全表并各自拥有展开预算，累积结果无总上限 | UID 例外索引；整文件及多来源共享组件、总迭代、输出数量预算；避免每 30 秒对未变内容完整重算 |
| Windows ICS 单次迭代不返回（CWE-835） | 不可满足的 DAILY 日期组合能让依赖内部搜索不返回，外部 25000 次计数无法抢占 | 整个解析、验证、迭代器初始化和展开放入可终止 Worker；主线程截止时间执行 terminate；导入/刷新失败保留旧数据 |

三项安全严重度均校准为 **Low**：需要用户导入本地文件，主要影响单个客户端可用性；未建立远程无交互触发、越权、RCE 或数据泄漏链。低安全严重度不等于不影响日常使用，文件供应方仍可诱导用户导入。

ICS 独立复现：正常规则约 0.299 秒返回两项；不可满足规则在外部 2 秒期限内未返回，由受控子进程终止，无残留进程。未用真实用户日历冻结应用。

**这些安全修复尚未完成统一验收。** 开始实施后发现另一条聊天正在同时编辑 GIF、Windows 日历和数据模块，已停止重叠写入。用户明确要求暂停本轮 Windows 修改。本轮不能把另一任务的实现或混合工作区的局部测试宣称为修复完成。

仍需注意：主线程上的 `Promise.race` 或 `setTimeout` 不能打断同步死循环；只添加全局事件数限制也不能中止一个不返回的 `iterator.next()`。刷新验证必须在替换和持久化旧日历之前成功。

未发现已证实的 XSS、命令注入、SSRF 或凭据泄露路径。Windows 的 HTML 转义、本地路径校验、固定 HTTPS 目标等已检查控制构成反证；这不意味着框架或所有未检查路径没有漏洞。

## 6. 界面与功能优化方向

### 保持当前紧凑主面板

实际观察到的 800 宽、200 高度上限、媒体/日历/托盘三列布局能正常显示基础内容，建议继续作为默认体验。不要自动切回仍在开发的新导航面板。

- 将主面板定位为快速查看与轻操作；完整笔记、任务历史和文件管理使用明确的详情入口，避免把所有列表压进 200 高度。
- 测试活跃任务卡片、较多组件、长歌曲标题、窄屏和大字号。现有旧布局固定紧凑网格，内容增加时没有充分的整体滚动保证。
- 顶部“媒体/日历/文件托盘”当前更像标签而非真正导航；应明确其含义，或让点击进入对应详情，避免看似可点却无反应。
- 新布局的 40+36 高度头部/导航在 200 高度下占比明显，详情最小内容高度又为 260；即使可滚动，也应专门做紧凑模式验收。
- 播放器未运行、权限未授权、无歌词、服务失败、加载中需要不同状态；不要统一落成“无曲目/没有歌词”。
- 提供“仅重置面板尺寸/交互”的恢复入口，避免用户为修正布局重置歌词、组件选择和其他偏好。

### 可访问性与设置

- 实际辅助功能树中，日历日期按钮没有可辨识名称；部分设置开关/滑块使用空标签。补充日期、选中状态、设置名称和当前值。
- 图标按钮应有可读名称及键盘操作；macOS 指针场景不机械套用手机触控尺寸，但应有足够命中范围和焦点反馈。[Apple 按钮说明](https://developer.apple.com/documentation/swiftui/button)建议为纯图标按钮保留可访问名称。
- 数字设置输入当前简单过滤字符，`-1`、`1e3` 等可能被改读为其他数值；应明确接受的格式并给错误反馈，而不是静默重解释。
- 建议将“显示与尺寸”“行为”“组件”“权限”“更新”组织为可搜索的小组，给危险恢复/清空操作单独确认。

## 7. 流畅度优化顺序

1. **消除可量化的主线程大任务**：批量关联只保存一次；较大历史编码移到后台快照；GIF读取/验证有界并避免重复解码。
2. **停掉不可见状态下的装饰刷新**：正式版与工作区的 GIF、滚动文字、鼠标轮询实现不同，应在暂停、面板隐藏、减少动态效果和屏幕休眠各状态测量。
3. **减少重复工作**：按内容/区间缓存日历解析；歌词候选可解析性尽量只计算一次；网络响应设大小上限和清晰的失败原因。
4. **建立同条件前后比较**：分别测空闲、播放、GIF、展开、批量资料关联，记录主线程占用、内存峰值、唤醒和耗时分位数，不用一次 CPU 读数替代性能验收。[Apple 性能优化流程](https://developer.apple.com/documentation/xcode/improving-your-app-s-performance)同样强调先测量，再针对瓶颈调整并复测。

## 9. 建议的后续执行批次

### 第一批：稳定性补丁

目标：保留原有面板和 200 上限，完成数据保护、日历跨日刷新、本轮媒体修复、GIF输入限制、设置入口与Cask一致性。

把已有可靠性修复从新版面板中拆出来；必要时适配旧视图调用，但不一并启用新导航。验收包括损坏数据保护、快速编辑退出、离线文件恢复、跨午夜、暂停/停止混合来源和异常GIF拒绝。

### 第二批：补齐操作闭环

补Spotify封面、失效笔记关联恢复、全部笔记/任务历史入口、控制失败反馈。每项先写实际用户流程和失败状态，再实现；不把“存在一个方法”视作功能完成。

### 第三批：性能与长期运行

减少重复持久化与解析，完成多屏、睡眠唤醒、长时间播放、网络短暂失败的验收。对照相同数据和操作记录前后指标，确认优化没有带来错曲、丢编辑或窗口抢焦点。

### Windows 独立批次

遵循用户要求，由另一条聊天统一整合本轮重叠改动。先消除当前类型/测试冲突，再验收 Worker 的不可满足规则超时、UI心跳、正常请求恢复、自动刷新失败不覆盖旧数据，最后进行实际 Windows WebView2 和安装器验收。
