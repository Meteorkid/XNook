## 一、结论先行：原拟发明点已被公开，必须收窄

上一版设计（`docs/LIVE-CAPTION-DESIGN.md`）把核心创新理解为：

> 把「识别进度」与「播放进度」解耦，让识别进度超前于播放进度，从而对可预取的音源同时获得离线级准确率与零感知延迟。

**这一核心思路在本次检索中已被完整公开，且公开日早于本报告的检索截止日。** 最接近的一份公开不是专利，而是一个开源项目：

- **Myna Player**，GitHub `ademisler/Myna-Player`，GPL-3.0-or-later，2026-08-02 通过技术文章、Product Hunt、LinkedIn、Mastodon 与仓库 README 公开。
- 其公开表述为「processes audio ahead of the current playback position」「transcribes it locally」「renders them against the native player clock」，并明确写出「It needs the prepared region to remain ahead of the playback clock. That turns the problem from instantaneous inference into scheduling.」

因此：

1. **不能**再把「提前转写 / 识别进度超前于播放进度 / 按播放位置给待转写区间排优先级 / 规范时间窗缓存 / seek 后保留已完成窗口 / 媒体指纹 + 管线配置键 / 按原生播放器时钟渲染」中的任何一项单独作为发明点。
2. 上述内容应当**主动写入拟申请文件的背景技术**，而不是回避。中国发明专利审查中，隐瞒最接近现有技术不会带来好处，反而影响答复审查意见时的可信度。
3. 剩余可主张的空间是**组合层面且必须高度具体化**：在「应用无关、音源身份可变的操作系统层」上，把「可预取性」作为一等调度属性，用「转写前沿与播放前沿之差」做闭环控制，并在音源切换/跳转时跨多条候选轨复用已有转写结果。详见 `docs/PATENT-DRAFT-系统级字幕调度.md`。
4. 需要清醒认识到：这是一个**组合发明**，单点均已有对比文件，创造性风险偏高。正式申请前应由代理师评估是否值得申请。

## 三、最关键的现有公开：Myna Player

| 维度 | 公开内容 |
| --- | --- |
| 公开日 | 2026-08-02（技术文章 Posted on Aug 2；Mastodon 2026-08-02 00:04；Product Hunt / LinkedIn 同期） |
| 许可证 | GPL-3.0-or-later |
| 状态 | public alpha，仓库 6 次提交，最新提交 2026-10-07 |
| 定位 | 自带播放器的本地媒体字幕应用（Rust / Tauri / Leptos / libVLC / FFmpeg / whisper.cpp） |

公开的技术特征逐条：

1. **提前于播放位置处理音频**：可从文件后段直接抽取音频，在播放到达前准备好字幕；明确论证「监听系统音频是错误抽象」，理由是本地文件可直接读取。
2. **持久优先级调度器**：按播放位置给窗口排优先级——首个所需窗口为紧急，其后约 90 秒提升优先级，更后区间作为后台任务。
3. **规范非重叠时间窗**：30 秒规范窗口作为缓存稳定身份，窗口间提取时额外读取约 2 秒邻域上下文，但持久化输出仍归属规范窗口，避免边界词丢失/重复。
4. **词级时间戳 + 原生播放器时钟渲染**：Whisper 本地产出词级时间戳，渲染器从不等待 AI 请求。
5. **媒体指纹 + 管线键**：指纹与所选音轨、模型哈希、语言模式、VAD 模型、分块参数、断句规则版本共同构成缓存键，仅键完全匹配才恢复检查点。
6. **seek 的 generation 机制**：取消在途 ASR/翻译连接 → generation 自增 → 保留已完成缓存 → 提升新区间优先级 → 拒绝旧 generation 的迟到结果。
7. **明确指出问题性质变化**：「不需要每个 AI 操作比人说话更快，只需要已准备区间始终领先于播放时钟；这把问题从瞬时推理变成调度。」

**与拟申请方案的重合**：第 1、2、3、4、5、6 项几乎逐条对应上一版设计的 `PrefetchTrack`、规范窗口缓存、重叠上下文、绝对时间戳、指纹锚定、跳转增量复用。

**其明确未覆盖的边界**（这是拟申请方案唯一可立足之处）：

- 只处理**本地媒体文件**，明确排除系统音频监听，因而不处理「音源身份未知或真正的直播」。
- 自带播放器，**不是应用无关的操作系统层能力**。
- 没有「可预取性」的判定与分级，因为其输入恒为可随机访问的本地文件。
- 没有在**可预取 / 不可预取两类音源之间热切换**识别轨与前瞻预算。
- 没有**平台字幕轨、预转写轨、流式轨**三条候选轨的统一时间轴仲裁。

## 七、中国发明专利客体与撰写规范（本次核实）

依据《专利审查指南（2023）》（2024-01-20 施行）第二部分第九章及国家知识产权局公开的常见问题解答：

1. **申请文件组成**：请求书、说明书及其摘要、权利要求书；有附图的应提交附图并指定摘要附图。摘要文字部分**不得超过 300 字**，不得使用商业性宣传用语。
2. **权利要求**：独立权利要求应记载解决技术问题的**必要技术特征**，通常包括前序部分与特征部分；从属权利要求包括引用部分与限定部分。本次修订明确允许以**计算机程序产品**作为保护主题，属产品权利要求，可写为「一种计算机程序产品，包括计算机程序/指令，其特征在于，所述程序/指令被处理器执行时实现……的步骤」。
3. **AI/算法类客体**：权利要求不得属于《专利法》第二十五条的智力活动规则和方法，且须满足第二条第二款的技术方案要求。仅在主题名称中出现「AI 芯片」等技术特征不足以克服该缺陷；关键看**主题名称之外的限定内容**是否包含技术特征。
4. **新增客体基准（指南 6.1.2）**：若算法与**计算机系统的内部结构存在特定技术关联**，解决「如何提升硬件运算效率或执行效果」的技术问题（包括**减少数据存储量、减少数据传输量、提高硬件处理速度**），获得符合自然规律的计算机系统内部性能改进的技术效果，则构成技术方案。**不要求对硬件作结构改动**——通过优化系统资源配置使整体获得内部性能改进即可。
5. **创造性**：算法特征与技术特征功能上彼此支持、存在相互作用关系时，创造性审查应考虑算法特征的贡献。**用户体验提升只有在由技术特征及与其相互作用的算法特征共同带来时**，才可作为创造性判断依据。
6. **充分公开**：AI 领域另有专门阐释，说明书须使本领域技术人员能够实现，技术效果需可验证、表述清楚。

**对本申请的写法约束**：

- 处理对象写成具有确切技术含义的数据：**音频数据、音频帧、音频指纹、音源描述符、播放时钟、绝对源时间戳**，而不是抽象的「字幕质量」。
- 「技术问题」写成：**在应用无关、音源身份可变的本地计算环境下，如何在有限算力与内存预算内，使多条候选字幕轨的转写进度持续覆盖播放进度，并避免音源切换与跳转引发的重复推理**。
- 「技术效果」写成可量化的系统内部性能：**减少重复转写次数、降低峰值内存占用、减少需常驻的音频缓冲数据量、降低本地推理单元占用率与功耗**。
- **不得**把「用户看得更准/更舒服」作为主要技术效果；它只能作为附带说明。
