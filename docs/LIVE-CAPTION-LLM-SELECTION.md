## 一、结论先行

本轮补做 4 组针对性检索，结论与上一版有一处实质冲突，**必须先收回**：

- **收回**：`LIVE-CAPTION-OPTIMAL-PIPELINE.md` 的 L2「用本地小 LLM 对低置信片段做文本层生成式纠错」不再推荐。中文公开实证显示直接纠错显著恶化字错误率，加保守门控后仍无净收益。
- **LLM 的正确位置是识别前，不是识别后**：让 LLM 由主题/意图生成少量动态偏置词，在解码前影响声学模型；以及只在可预取音源上做全片实体一致性归纳。两处都不在逐句实时路径上。
- **同音字纠正交给拼音/音节约束层**，不交给自由生成。这类机制在中文上有明确正向数据，且成本、延迟、幻觉风险都低于 LLM。
- **换 ASR 引擎的收益可能大于加纠错层**：中文专名场景，为中文优化的中小模型明显优于 Whisper large-v3-turbo。但是否可流式、能否在 macOS/MLX 上运行，本轮未验证，暂只列入可预取离线轨。
- **本地 LLM 不是「一律太慢」**，而是取决于 prompt 长度与冷热状态。不过既然逐句纠错本身负收益，延迟已不是决定因素，**正确性才是**。

一句话：**LLM 要站在「给识别器提供线索」的位置，不要站在「替识别器改稿」的位置。**

## 二、本轮补充检索与关键证据

### 2.1 中文 LLM 纠错的负结果（决定性）

`Selective Gating for LLM-Based Chinese ASR Error Correction`（JBDC 2026）在 Common Voice zh-CN 上用 Whisper-small 出假设、Qwen2.5-3B-Instruct 做纠错，100 句开发集调参、1000 句独立测试集冻结评估：

| 方案 | Macro CER | 变差句数 |
| --- | --- | --- |
| Whisper 基线 | 34.75% | — |
| 直接 LLM 纠错 | **44.75%** | 469 |
| edit-ratio + ASR 置信度联合门控 | 34.79% | 5 |

联合门控把「越改越坏」的句子从 469 压到 5，但 Macro CER **仍略高于基线，没有净收益**。论文结论：小的通用指令微调 LLM 不是可靠的无条件 ASR 后处理器；保守门控只能限制错误传播，需要更可靠的错误检测与命名实体保护才能产生增益。

这直接否掉了「低置信 → 小 LLM 改写」这一层。注意该实验用的是 small 级 ASR + 3B LLM，基线 CER 偏高，不能直接外推到 large-v3-turbo；但方向性证据足够强：**在拿到自己的评测集证明净收益之前，不应把逐句 LLM 纠错放进默认链路。**

### 2.2 门控所依赖的「置信度」本身不可靠

一份中文 ASR 实测笔记给出同一段 60 秒中文素材的专名正确率：

| 引擎 | 专名正确 |
| --- | --- |
| Whisper large-v3-turbo | 2/11 |
| Fun-ASR-Nano（约 800M） | 10/11 |
| Qwen3-ASR 1.7B | 7/11 |

典型错误：肇庆→赵庆、怀集→淮吉、利玛窦→立马逗。笔记明确提示 **Whisper 的错可能是高置信度错，不能只看置信度判断质量**；并指出最危险的是「错写本身仍是合法中文词」（姚顺雨→尧舜禹），模型读到不会起疑。

因此上一版设计的 `avg_logprob` 低置信门控，会同时漏掉最该修的专名错误、又放进来一批不该改的句子。门控信号必须换成多源的：拼音/音节一致性、实体表匹配、跨引擎结果不一致、N-best 分歧、词级置信度的离散程度。

同一笔记还给出一条值得沿用的收益口径：**纠错层真实价值 = 覆盖率 × 漏改率**，只算覆盖率会把「人工本来就改对的」算成收益；按此口径，笔记把几个看似有前景的本地纠错方案算到 2%–4%，判定不值得投入。

### 2.3 正向证据在识别前：LLM 生成偏置词

`Improving Contextual Biasing in Chinese ASR via Multimodal Large Language Models`（IEEE Access 2026）研究中文专名（地名、人名、歌名、影视名）在同音字干扰下的识别问题，做法是：

1. 微调多模态 LLM 做端到端意图识别，相对未微调模型错误率降低 81.82%，相对级联模型降低 66.71%；
2. 依据高准确率的意图预测，**动态生成与上下文相关的关键词提示**，在识别前引导 ASR；
3. 结果关键词错误率 KER 相对降低 **41.48%**；冷启动用「专名清单 → 小语言模型造自然句 → 语音合成」自动生成训练数据，效果 41.91%，接近真实标注数据。

这才是「结合 LLM」有证据支撑的形态：**LLM 输出的是线索，不是字幕**。它的输出可以错、可以晚、可以低频触发，因为错了最多是偏置词没命中，不会把已识别对的字幕改坏。这与实时链路天然解耦。

### 2.4 本地 LLM 延迟：不是绝对障碍，但决定触发方式

上一版判断「LLM 太慢，不能进实时路径」过于笼统。本轮拿到的数据分歧很大，差别主要来自 **prompt 长度与冷/热状态**：

| 来源与条件 | 模型 | TTFT | 解码速度 |
| --- | --- | --- | --- |
| 社区实测，含 warmup，三种 prompt 平均 | Llama 3.2 3B 4-bit | **89 ms** | 226.7 tok/s，峰值 2.06 GB |
| 同上 | Qwen2.5 7B 4-bit | 115 ms | 117.2 tok/s |
| 参考跑分，冷启动约 2K prompt，M4 Pro | Llama 3.2 3B 4-bit | **2.2 s** | 121.2 tok/s |
| 同上 | Qwen3 4B 4-bit | **2.9 s** | 93.0 tok/s |
| 同上 | 0.6B / 1.2B 级 4-bit | 0.5 s / 0.8 s | 384 / 314 tok/s |
| 估算表，4K prompt，M4 Max 36 GB | 3B 4-bit | 200–400 ms | 60–80 tok/s |

结论要精确成三句话：

1. **热模型 + 短 prompt（约 200 token 内）可做到约 100 ms 首 token**，本地 3B 4-bit 在 M3 Max / 36 GB 上常驻完全可行；
2. **冷启动或 2K 级 prompt 会到 2–3 s**，任何把长上下文（全片实体表、长 N-best 列表）塞进逐句 prompt 的设计都会崩；
3. 但**这些数字不该成为把 LLM 放进主链路的理由**——2.1 已说明该位置本身无净收益。延迟约束在这里只是进一步要求「常驻 + 短 prompt + 低频触发」，不是设计目标。

### 2.5 MLX 与 AlignAtt 的组合边界（一个需要说清的细节）

上一版把「MLX Whisper + SimulStreaming/AlignAtt」并列写成可用组合，需补一处限定。WhisperLiveKit 的参数表显示：

- `--backend auto` 在 macOS 检测到 MLX 时优先选 MLX；可显式指定 `mlx-whisper` / `faster-whisper` / `whisper` / `openai-api`（后者仅 LocalAgreement 可用）；
- SimulStreaming 段有 `--disable-fast-encoder`，说明是「禁用 Faster-Whisper 或 MLX-Whisper 后端作为**编码器**」；
- AlignAtt 依赖在解码器上安装 cross-attention forward hooks 读取注意力权重，因此解码器仍是原生实现。

所以准确说法是：**MLX 加速编码器 + 原生解码器跑 AlignAtt**，不是「整条流式链路跑在 MLX 上」。这不影响可用性，但影响内存与部署估算。

另有三点工程约束：

- 旧版 README 明确写过「simulstreaming 工作不正常时可切 faster-whisper」，说明该后端存在稳定性风险，**必须保留 LocalAgreement 降级轨**；
- 由于全局 forward hooks 不能共享，**每个连接需独立模型实例**，并靠 `--preload-model-count` 预载。系统级单用户单实例恰好契合，但模型必须常驻，不能按需加载；
- 偏置相关参数原生可用：`--init-prompt`、`--static-init-prompt`（跨段不滚动）、`--max-context-tokens`（通常 448）、`--frame-threshold`（默认 25 帧 ≈ 0.5 s，调小更低延迟更激进）、`--cif-ckpt-path`（只在词边界输出，避免吐半个词）、`--beams`。**这意味着「实体表 → 识别前偏置」在流式路径上不用自己造轮子**，是 2.3 结论能直接落地的原因。

`--comp_unaware`（计算无感知）模式可测延迟下界，正好用于第八节评测集。

### 3.3 同音字为什么交给拼音层

`Contextual Biasing with Confidence-based Homophone Detector for Mandarin`（CBCB）提供了一条比 LLM 更贴合中文错误的路径：先把偏置建模在**音节**而非字符上，使错误保持音系一致（「更好改的错」）；再用置信度分数的**变异系数 CV** 检出「峰状不稳定分布」的同音替换，配合拼音 + 编辑距离从上下文词表取候选替换。Aishell-1 上偏置词 CER 降低 52%，整体 CER 相对改善 31.2%；与 Shallow Fusion 级联后 13.9% → 8.00%。

它和 LLM 纠错的差别是结构性的：候选来自**封闭词表**、改动力受**拼音/音素一致性**约束、判定来自**统计离散度**而非语言模型的自由生成，因此不会把「姚顺雨」改成别的合法词，也不会把口语改书面语。代价是需要维护实体词表——而这正好由 3.2 的「用户纠错闭环 + 全片实体归纳」提供。

> FLEURS 中文 CER 参考量级（二手转述官方数据，未复核原始评测）：Qwen3-ASR 1.7B 约 7.1%、Whisper large-v3-turbo 约 8.5%、Fun-ASR Nano 约 8.6%、SenseVoice Small 约 10.1%、Whisper medium 约 13.1%。**整体 CER 与专名正确率不是一回事**，选型不能只看前者。

## 四、推荐架构

三条链路按**音源可预取性**分派，统一由绝对源时间戳索引，输出前过同一套三态修订协议。

### 4.1 实时主链路（不可预取音源：直播、会议、通话）

```
系统音频 / 媒体流 → L0 覆盖图（本地缓存查询）
  → 缺口区间 → Silero VAD → SimulStreaming / AlignAtt（MLX 编码器）
  → 词级时间戳映射到绝对源时间 → 三态合成 → 浮层输出
                      ↓ 异常
              LocalAgreement-2 降级轨 / SpeechAnalyzer 兜底
```

参考启动参数（WhisperLiveKit 0.2.16 口径，具体以实际版本为准）：

```
--backend auto --backend-policy simulstreaming --language zh
--model large-v3-turbo --frame-threshold 25 --no-vac 关闭不推荐
--static-init-prompt "<会话级实体词表，5–10 个短词>"
--max-context-tokens 448 --cif-ckpt-path <词边界模型>
--preload-model-count 1 --warmup-file <预热音频>
```

要点：`static-init-prompt` 承接 LLM 与用户词典产出的偏置词；`cif-ckpt-path` 保证不在词中间吐字；`preload-model-count 1` 对应单实例常驻。**LLM 不在此链路中。**

### 4.2 近线 / 会话级链路（两类音源共用）

不逐句触发，按会话或按话题段触发：

1. 汇总已稳定字幕、用户纠错、平台元数据，归纳出**实体候选表**；
2. 本地 3B 级 4-bit 模型做一次意图/主题归纳，产出 5–10 个偏置词（词表过长会让模型在近音词间犹豫，反而拉低整体准确率）；
3. 写入 `static-init-prompt` 与拼音词表，供后续解码使用；
4. 同音字候选替换由拼音约束层完成，**不调用生成式改写**。

这一层可以用 LLM，因为它的输出是「线索」，错了不污染字幕；且低频触发，2.4 节的冷启动延迟不敏感。

### 4.3 可预取离线链路（点播、本地文件、可提前拉取的流）

播放前跑完：L0 多来源覆盖图 → 空白区间全片预转写（large-v3-turbo，中文专名密集段落可切中文优化引擎）→ 全片实体表 + 一致性投票 → 写缓存 → 播放时纯读取，零感知显示延迟。

LLM 在此链路允许做：术语表归纳、实体聚类、断句与标点规范化。**仍不允许无条件改写字幕正文**；所有改动须来自封闭候选集并保留原文可回退。

### 4.4 明确不做

- 不把自由生成式 LLM 放在毫秒级主链路；
- 不允许 LLM 无条件改写已识别文本，不把「润色」当功能；
- 不用单一 ASR 置信度作为纠错门控；
- 不做双引擎全量并行 + 特征级拼接（算力与既有专利风险）；
- 不把云端 ASR 作为默认路径。

## 五、LLM 接入规范

### 5.1 三个允许位置

| 位置 | 触发时机 | 输入 | 输出 | 失败后果 |
| --- | --- | --- | --- | --- |
| 识别前 · 偏置词生成 | 会话开始 / 话题切换 | 元数据、已稳定字幕摘要、用户词典 | 5–10 个实体词（封闭列表） | 偏置未命中，字幕不受影响 |
| 全片 · 实体一致性归纳 | 仅可预取，播放前 | 全片首轮转写 + 词级置信度 | 实体规范形 + 出现位置 | 退化为不替换 |
| 全片 · 断句与标点 | 仅可预取，播放前 | 已稳定字幕序列 | 分句与标点 | 退化为原始分块 |

三者共同特征：**输出可丢弃、改动可回退、不在逐句路径上**。这是能否上线的准入条件，比 prompt 里写「请不要乱改」有效得多。

### 5.2 数据结构（偏置词生成，非逐句纠错）

```text
BiasRequest {
  session_id
  media_descriptor            // 不含音频正文
  topic_hint                  // 标题、频道、章节名等元数据
  stable_transcript_digest    // 已稳定字幕的摘要，长度上限 200 token
  user_dictionary[]           // 用户确认过的专名
  max_entities: 10
  allowed_output: enum { entity_list }
}

BiasResponse {
  entities[] {
    surface                   // 规范写法
    pinyin_syllables[]        // 用于音节级匹配
    category                  // 人名 / 地名 / 术语 / 作品名
    source                    // metadata | user | transcript
  }
  expires_at                  // 会话结束或话题切换即失效
}
```

注意请求里**不放音频、不放逐句文本**；输出只允许枚举类型，不允许自由文本。这样既限制了幻觉面，也把 prompt 压在 2.4 节能达到约 100 ms TTFT 的短上下文范围内。

同音字替换单独走另一条结构，候选来自封闭集：

```text
HomophoneCandidate {
  cue_id
  source_timestamp_range
  original_text
  pinyin_syllables[]
  entity_candidates[]         // 来自实体表，含拼音与来源等级
  confidence_dispersion       // 词级置信度变异系数 CV
  multi_engine_disagreement   // 跨引擎不一致标志
  allowed_operations: enum { keep, replace_from_candidates }
}
```

判定逻辑：仅当 `entity_candidates` 与 `pinyin_syllables` 匹配、且 CV 或多引擎分歧给出异常信号时，才允许 `replace_from_candidates`；其余一律 `keep`。**没有「让模型自己写一个更好的词」这个操作。**

### 5.3 门控与上线准入

按 2.2 的教训，门控信号优先级从高到低：

1. 拼音/音节与封闭实体表的匹配；
2. 跨引擎结果不一致、N-best 分歧；
3. 词级置信度的离散程度（CV），而非单一置信度阈值；
4. 用户词典显式命中（最高优先，直接采纳）；
5. `avg_logprob` 仅作辅助信号，**不得单独使用**。

上线前必须有量化准入：在自建中文评测集上，任何纠错层都要证明 **净 CER 下降**且「变差句数」不上升；只报告「改对了多少句」不算数。同时监控改写率、回退率，并保留原文与时间戳。

### 评测集（前置条件）

沿用此前建议：20–30 段中文视频，覆盖有字幕 / 无字幕 / 部分字幕 / 直播四类，重点包含人名、地名、产品名密集片段。至少量化四个指标：

- 零推理区间占比（L0 的真实收益）；
- CER 与**专名正确率**（必须分开报，2.2 已说明二者不等价）；
- 端到端呈现延迟（用 `--comp_unaware` 测主链路延迟下界，再测真实链路）；
- 纠错层的**变差句数**与净 CER 变化（不能只报改对句数）。

另需实测本机 M3 Max / 36 GB 上的：3B 4-bit 模型热态短 prompt TTFT、SimulStreaming 在 `frame_threshold` 取 15/25/40 时的延迟与 CER 曲线、常驻模型对功耗与风扇的影响。本轮所有数字均为外部公开数据，未在本机复现。
