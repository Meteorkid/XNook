# X Nook 实时字幕引擎设计方案

> 目标：系统级、音源无关的通用字幕能力。不针对任何单一平台。
> 状态：设计稿 · 2026-11-13
> 目标机器：Apple M3 Max / 36 GB / macOS 26.7

---

## 一、第一性原理：准确率的真实自变量

### 1.1 修正一个常见误解

行业里常被表述为"实时与准确不可兼得"。这个表述不精确，会导致错误的架构决策。

**准确率的真实自变量是「可用前瞻深度」（available lookahead）——即识别某个词时，模型能够看到的、位于该词之后的音频时长。**

形式化：

```
accuracy = f(lookahead)
其中 f 单调递增，且在 lookahead ≥ 5s 后趋于饱和
```

- `lookahead = 0`：只能依据当前词及之前的内容解码，同音字、专有名词必然出错
- `lookahead = 3–5s`：看到完整句子结构，可消解大部分歧义，进入甜点区
- `lookahead = 全文`：等价于离线转写，准确率上限

### 1.2 由此得出的关键推论

**"实时"与"准确"之所以看似互斥，是因为传统实现把 `lookahead` 与"音频到达时间"绑定了。**

打破这个绑定的唯一方式是：**让识别进度超前于播放进度**。这要求音源具备「可预取性」（prefetchability）。

据此，所有音源可分为两类，这是整个架构的判定根基：

| 类别 | 定义 | 可用前瞻 | 可达准确率 |
|---|---|---|---|
| **可预取音源** | 音频在播放前已完整存在或可提前缓冲 | 无上限 | 离线级 |
| **不可预取音源** | 音频在播放时尚未产生 | 受固定延迟约束 | 接近离线级 |

- **可预取**：本地视频/音频文件、已缓存完成的流媒体、录播内容、B 站等平台的点播视频
- **不可预取**：直播、实时会议、语音通话、麦克风输入

**这是本方案的核心分野。任何单一模式的设计都无法覆盖两类音源，必须双轨。**

### 1.3 对"不可预取"音源的正确期望

即使无法预取，也不意味着只能接受低准确率。正确做法是**用固定延迟换取前瞻深度**：

- 字幕显示落后音频 2–3 秒
- 每个词在展示前已经"看过"后续 2–3 秒的语境
- 代价是延迟，收益是接近离线的准确率

业界参照：广播级实时字幕标准延迟约 2–3 秒；Whisper-Streaming（LocalAgreement-2 策略）在 ESIC 测试集上实测 3.3 秒延迟。

**关键认知：对于字幕这种阅读型内容，2–3 秒的稳定延迟，用户体验显著优于 0.2 秒的抖动延迟。**

## 二、能力上限与硬约束

### 2.1 硬件余量（本机实测）

| 项目 | 数值 | 含义 |
|---|---|---|
| 芯片 | Apple M3 Max，30 核 GPU | 支持 Metal 4，MLX 全速 |
| 统一内存 | 36 GB | 可并行驻留多个识别实例 |
| MLX Whisper large-v3 | 约 3–4 倍实时，占 3.0 GB | 1 小时音频约 15–20 分钟转完 |
| MLX Whisper tiny | 50 倍以上实时，占 150 MB | 用于实时草稿轨 |
| MLPerf v5.1 边缘端 | M3 Max RTF@WER20% = 0.05 | 能效比第一 |

**结论：本机算力足以支撑"快慢双模型并行"架构。**

### 2.2 识别引擎能力对照

| 引擎 | 延迟 | 准确率 | 语言覆盖 | 内存 | 适用轨道 |
|---|---|---|---|---|---|
| **Apple SpeechAnalyzer** | 极低（~200 ms） | 中高 | 42 locale / 22 语言 | ~140 MB | 实时草稿轨 |
| **MLX Whisper large-v3** | 高（需前瞻） | 最高 | 99+ 语言 | 3.0 GB | 预转写轨 / 精修轨 |
| **MLX Whisper tiny** | 极低 | 低 | 99+ 语言 | 150 MB | 实时草稿轨备选 |
| **Parakeet** | 低 | 高（仅英文） | 英文 | ~1 GB | 英文场景专用 |

**SpeechAnalyzer 关键数据**：
- LibriSpeech WER 2.12%，对比旧版 SFSpeechRecognizer 9.02%
- 中文（zh_CN）、繁体（zh_TW）、中国香港（zh_HK）、粤语（yue_CN）均在支持列表
- 系统自带模型，无需下载、无需联网、无 API Key
- **限制**：不支持自定义词汇表（hotword），这是必须用 Whisper 补位的原因

### 2.3 系统级硬约束（必须接受，无法绕过）

| 约束 | 影响 | 应对 |
|---|---|---|
| **DRM 保护内容** | ScreenCaptureKit 对受保护流直接跳过，表现为黑屏/静音 | 无法绕过。此类内容需回落到平台字幕或虚拟声卡 |
| **系统静音时** | 捕获到的是静音信号 | 提示用户不要静音；耳机播放不受影响 |
| **屏幕录制权限** | 与系统音频录制共用同一 TCC 权限项 | 首次使用需授权，且**必须完全退出 App 后重启才生效** |
| **授权对象是启动进程** | 从终端启动时权限归属终端而非 App | 开发期用 `.app` 包启动，而非直接跑二进制 |
| **临时签名导致权限重置** | Ad-hoc 签名每次构建 CDHash 变化，TCC 视为新应用 | 用稳定的 Apple Development 证书签名 |
| **虚拟音频处理器引入回声** | Krisp、SoundSource 等会延迟约 50 ms 重发音频 | 检测并提示用户关闭 |

## 三、总体架构

### 3.1 分层视图

```
┌─────────────────────────────────────────────────────────────┐
│  L5  呈现层   CaptionOverlay                                │
│       · 刘海区渲染 · 独立浮层 · 字幕窗口 · 导出             │
├─────────────────────────────────────────────────────────────┤
│  L4  合成层   CaptionComposer                               │
│       · 稳定段锁定 · 易变段修正 · 修订协议                  │
├─────────────────────────────────────────────────────────────┤
│  L3  偏置层   ContextBiasEngine                             │
│       · 热词注入 · 领域词典 · 首轮结果回灌 · 用户纠错学习   │
├─────────────────────────────────────────────────────────────┤
│  L2  识别层   RecognitionOrchestrator                       │
│       ├── PrefetchTrack   预转写轨（Whisper large-v3）      │
│       ├── StreamingTrack  实时流式轨（SpeechAnalyzer + 精修）│
│       └── PlatformTrack   平台字幕轨（已有字幕源）           │
├─────────────────────────────────────────────────────────────┤
│  L1  音频层   AudioBus                                      │
│       · 多源捕获 · 重采样 · 时钟对齐 · VAD 分段              │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 轨道调度决策

调度器依据音源特征自动选择轨道，**而非由用户手动配置**：

```
输入：音源描述符（来源类型、时长、可否 seek、是否有字幕轨）

若 存在平台字幕轨          → PlatformTrack（零算力，最高优先级）
若 音源可预取 且 时长已知  → PrefetchTrack（离线级准确率）
否则                       → StreamingTrack（固定延迟换准确率）
```

**降级链路**：`PlatformTrack` 失败 → `PrefetchTrack`（若可预取）→ `StreamingTrack`
**升级链路**：`StreamingTrack` 运行中若检测到音源转为可预取（如直播结束生成回放），自动切至 `PrefetchTrack` 重算。

## 四、音频层设计（L1）

### 4.1 多源捕获策略

按优先级选择捕获后端，**运行时探测能力而非硬编码**：

| 优先级 | 后端 | 最低版本 | 权限 | 说明 |
|---|---|---|---|---|
| 1 | **Core Audio Process Tap** | macOS 14.2 | 无需屏幕录制权限 | 可精确到单个进程；延迟可低于 20 ms |
| 2 | **ScreenCaptureKit** | macOS 12.3 | 需屏幕录制权限 | 稳定性更好，适合长时间录制 |
| 3 | **AVAssetReader** | — | 无 | 本地文件直读，音质无损 |
| 4 | BlackHole 虚拟声卡 | — | 麦克风权限 | 兼容层，仅用于 DRM 场景兜底 |

**关键工程结论（来自多份生产实践）**：

- **长时录制优先 ScreenCaptureKit**：`SCStream` 的时钟由系统合成混音驱动，长时间运行更稳。`CATap` 的 IO 回调由硬件输出设备时钟驱动，若输出设备空闲、被 HFP 占用或停滞，会静默停止供数——已有产品从 CATap 回退到 SCStream 的案例。
- **需要亚 20 ms 延迟时才用 CATap**（实时 AEC、实时分析场景）。
- **两者不混用**：对 `AVAudioEngine` 调用 `setVoiceProcessingEnabled(true)` 会创建隐藏的 VPIO 聚合设备，劫持系统输出路径作为回声参考，导致 `SCStream` 的系统音频被静音，同时把所有其他音频压低约 20 dB。

### 4.2 ScreenCaptureKit 纯音频捕获的正确写法

`ScreenCaptureKit` 没有官方文档化的"纯音频模式"。可用 `capturesAudio = true` 且只挂 `.audio` 输出，但有两个陷阱：

```swift
let config = SCStreamConfiguration()
config.capturesAudio = true
config.sampleRate = 48_000
config.channelCount = 2
config.excludesCurrentProcessAudio = true   // 排除自身 UI 音效，避免自激

// 陷阱 1：视频管线始终运行。不挂 .screen 输出会持续刷 "stream output NOT found" 日志。
//         必须挂一个忽略缓冲的 .screen 输出，并放在独立队列，确保视频永不阻塞音频。
// 陷阱 2：minimumFrameInterval 是「最小帧间隔」，值越大帧率越低。
//         CMTime(value: 1, timescale: .max) 约等于 0.5 ns，会被解读为「请求最高帧率」——
//         已有产品因此跑满 60 fps 重合成。正确写法是 1 fps。
config.width = 2
config.height = 2
config.minimumFrameInterval = CMTime(value: 1, timescale: 1)

let stream = SCStream(filter: filter, configuration: config, delegate: self)
try stream.addStreamOutput(self, type: .screen, sampleHandlerQueue: videoQueue)  // 忽略其数据
try stream.addStreamOutput(self, type: .audio,  sampleHandlerQueue: audioQueue)
```

**性能实测**：原生刷新率下 5K 显示器重合成约占单核 15–20%（含 app、`replayd`、`WindowServer`）。限速至 1 fps 后可忽略。

**健壮性要求**：`SCStream` 出错后不可复用。`didStopWithError` 后 XPC 连接已断，对同一对象调用 `startCapture()` 会抛 `attemptToStartStreamState`。必须置空并重建。

### 4.3 音频归一化

所有后端统一输出：**16 kHz / 单声道 / Float32**（Whisper 与 SpeechAnalyzer 的原生输入格式）。

- 48 kHz 立体声 → 16 kHz 单声道，重采样使用 `vDSP` 或 `rubato`
- 音频回调线程只做拷贝，**解码与重采样全部移出音频线程**，避免阻塞
- 每个缓冲携带 sample-accurate 时间戳，用于跨轨对齐

### 4.4 语音活动检测（VAD）

**Silero VAD** 前置过滤，作用有三：

1. 静音段不进识别，**消除幻觉输出**（风扇声、背景音乐被误识别为语音是实时字幕最常见的质量问题）
2. 显著降低算力消耗
3. 提供自然断句点，避免在词中间切断

**分段策略**：不用固定窗口。采用**重叠滑动窗口 + 静音优先断句**：
- 默认窗口 15 s，步进 1 s（保证 `lookahead ≥ 5s`）
- 检测到 ≥ 400 ms 静音时优先在此处切分
- 相邻窗口重叠部分的重复文本在合成层去重

## 五、识别层设计（L2）

### 5.1 PrefetchTrack — 预转写轨（可预取音源）

**核心机制：识别进度与播放进度解耦。**

```
时间轴 →
播放:   |==========>
识别:   |========================================>
        └─ 识别始终领先播放，领先量 ≥ lookahead 需求
```

**执行流程**：

1. 播放启动前，先转写前方 **60–120 秒**（M3 Max 上约需 15–30 秒）
2. 字幕缓冲就绪后开始播放，用户感知延迟为零
3. 后台继续转写后续内容，始终维持领先量
4. 转写完成后，整段结果落盘为 SRT/VTT，后续重播直接读缓存

**准确率优化手段（按收益排序）**：

| 手段 | 收益 | 实现方式 |
|---|---|---|
| 全文前瞻 | 基准 | 天然具备 |
| **术语偏置** | B-WER 降低 43–70% | `initial_prompt` 注入领域词典 |
| **首轮结果回灌** | 相对 WER 降低 17% | 用粗转写结果提取实体，二次解码 |
| 用户词典 | 持续提升 | 记录用户纠错，累积热词 |
| 大模型后编辑 | 视领域而定 | 可选，本地 LLM 修正术语 |

**关于 `initial_prompt` 的工程要点**（这是最易被误用的参数）：

- 上限约 224 token，但**生产环境应控制在 50 token 以内**——提示词直接占用解码上下文预算，过长会挤占实际语音分析空间，反而降低准确率
- **逗号分隔的实体列表优于完整句子**——完整句子会诱导自回归解码器把提示词内容复述进转写结果
- **稀有词放在末尾**——只有最后 ≤224 token 生效
- 提示词是**概率性软引导，不是硬约束**——音频明确说的是别的内容时，模型会覆盖提示词
- 多说话人/嘈杂音频下，提示词**可能引入假阳性**（把未出现的词强行插入）。上线前需用 5–10 个样本验证

**回灌流程**（两遍解码）：

```
音频 → 第一遍粗转写（medium 模型，快）
     → NER 抽取候选实体 + 术语抽取
     → 与领域词典做模糊匹配（编辑距离 + Jaro-Winkler，阈值约 0.85）
     → 构造紧凑提示词（≤ 50 token）
     → 第二遍精转写（large-v3 + initial_prompt）
     → 输出
```

### 5.2 StreamingTrack — 实时流式轨（不可预取音源）

**采用"快慢双模型"架构，兼顾即时反馈与最终准确率。**

```
音频流 ──┬──> 快轨：SpeechAnalyzer ──> 草稿字幕（~200 ms 延迟，灰色显示）
         │
         └──> 慢轨：Whisper large-v3（3 s 前瞻）──> 定稿字幕（2–3 s 延迟，白色显示）
```

**用户感知**：文字立即出现（草稿），2–3 秒后被精修版本替换。若用户不逐字盯读，主要感知到的是精修版本。

**慢轨的流式策略**：采用 **LocalAgreement-2**（最长公共前缀确认法）

```
更新 N-1:  "今天我想感谢 Brejc 先生的精彩报告。"
更新 N:    "今天我想感谢 Brejc 先生的精彩报告。我们感谢"
                          └────── 最长公共前缀 ──────┘
输出:      "今天我想感谢 Brejc 先生的精彩报告。"  ← 仅确认公共前缀
           "我们感谢"                            ← 保留为待确认
```

**策略选型对照**：

| 策略 | 延迟 | 准确率 | 依赖 | 选用 |
|---|---|---|---|---|
| LocalAgreement-2 | 中（3.3 s） | 高 | 无 | ✅ 主选 |
| LocalAgreement-Levenshtein | 中 | 略高 | 无 | 备选（编辑距离放宽版） |
| AlignAtt | 低 | 高 | 需模型注意力可见 | 需替换推理栈，暂不采用 |
| 固定分块 | 高 | 低（边界切词） | 无 | ❌ 不采用 |

**性能优化**（SimulStreaming 的四项关键手段，均可独立借鉴）：

1. **KV 缓存复用**：跨 Whisper 的 30 s 处理窗口保留 decoder KV，避免每段从头重算
2. **词尾检测剪枝**：判断段尾是否为半截词，是则剪掉——半截词大概率错误，直接减少返工
3. **跳过静音**：VAC 控制器让模型只在有人声时工作
4. **注意力引导解码**：划定安全边界，注意力越过即停手

### 5.3 PlatformTrack — 平台字幕轨

对已有字幕的内容，**直接取用是最优解**：零算力、零延迟、准确率由平台侧保障。

设计上不针对特定平台硬编码，而是抽象为**字幕源适配器接口**：

```swift
protocol CaptionSourceAdapter {
    static func canHandle(_ descriptor: MediaDescriptor) -> Bool
    func fetchCaptions(for descriptor: MediaDescriptor) async throws -> [CaptionCue]
}
```

各平台以插件形式实现。通用注意事项：
- 多数平台的 AI 字幕接口需要**登录态凭证**，匿名请求返回空
- 字幕资源 URL 通常带**分钟级有效的签名**，需即时下载
- 字幕 JSON 结构普遍为 `{from, to, content}` 三元组数组，可直接映射为内部 `CaptionCue`

**重要**：平台字幕同样存在错误（专有名词、数字尤为常见）。本轨道的价值在于省算力与降低延迟，而非"保证准确"。

## 六、偏置层设计（L3）

这是把"能识别"提升到"识别得准"的关键层，也是多数开源实现缺失的一层。

### 6.1 四类上下文来源

| 来源 | 获取方式 | 生效时机 |
|---|---|---|
| **全局领域词典** | 用户配置 / 内置词库 | 会话开始前注入 |
| **场景词典** | 按当前前台 App 匹配（IDE / 浏览器 / 会议软件） | 会话开始前注入 |
| **首轮结果回灌** | 粗转写 → 实体抽取 | 精修阶段 |
| **用户实时纠错** | 用户在字幕上直接修改 | 立即注入后续窗口 |

### 6.2 词典构建原则

从参考文档自动抽取术语时，必须**严格约束抽取规则**，否则会得到无偏置价值的通用词：

- **只抽多词术语**（2–4 词），排除通用单词名词（"数据"、"系统"、"云端"）
- **保留缩写与驼峰命名的大小写原样**
- **输出为逗号分隔列表**，而非自然语言句子
- 抽取来源限定为**当前文档/当前页面**，避免引入外部未验证内容造成幻觉

### 6.3 反馈闭环

```
用户纠错 → 提取被改词对 → 累积至个人词典
         → 阈值达标后进入全局词典 → 后续会话自动生效
```

此闭环是系统随使用时间**持续变准**的唯一来源。没有它，准确率将永久停留在模型出厂水平。

## 七、合成层设计（L4）：修订协议

这是决定体验成败的一层。核心问题是：**字幕已经显示出来了，但后续语境证明它是错的，怎么办？**

### 7.1 状态模型

每个字幕单元有三种状态：

| 状态 | 视觉呈现 | 可变性 |
|---|---|---|
| **Volatile**（易变） | 灰色 / 半透明 | 可被替换 |
| **Stable**（稳定） | 白色 / 实心 | 不可变 |
| **Corrected**（已修正） | 白色，短暂高亮 | 不可变 |

### 7.2 状态跃迁规则

```
新文本 → Volatile
Volatile ──[被后续 2 次识别结果确认为相同前缀]──> Stable
Volatile ──[被后续识别结果推翻]──> 替换后重新判定
Stable   ──[精修轨给出不同结果]──> Corrected（保留修订记录）
```

### 7.3 三条硬性约束（防止视觉抖动）

1. **永不回溯超过 N 个字符**：建议 N = 15。超出则不再修正，改为记录到日志供用户事后查看
2. **永不修正已 Stable 超过 T 秒的内容**：建议 T = 5 s。用户可能已读走
3. **修正幅度超过阈值时降级处理**：若修正涉及整句重写，不原地替换，而是作为新行追加并标注

### 7.4 时间轴对齐

字幕与音频的对齐误差必须控制在 **±200 ms** 内，否则产生明显的"口型不同步"感。

- 所有字幕单元携带**源音频的绝对时间戳**（而非相对窗口时间）
- 跨轨切换时（如草稿轨 → 精修轨），以时间戳为准做映射，不做顺序假设
- 窗口重叠区的重复文本，按时间戳去重而非文本去重（同音词可能文本相同但时间不同）

## 九、权限与合规

### 9.1 需要补充的配置

当前 `Info.plist` 缺失以下项，实现字幕功能时必须补齐：

```xml
<key>NSScreenCaptureUsageDescription</key>
<string>X Nook 需要捕获系统音频以生成实时字幕。</string>
```

`XNook.entitlements` 当前已含 `files.bookmarks.app-scope` 与 `automation.apple-events`，**无需新增 entitlements**（音频捕获走 TCC 授权，不走 entitlements）。

### 9.2 权限申请的正确姿势

**这是一个已知的踩坑点**：`CGPreflightScreenCaptureAccess()` 只检查、不申请。若用它做前置守卫，会陷入死循环——因为从不申请，所以永远不会出现在系统设置的授权列表中。

正确做法：

```swift
// App 启动时主动申请，使其出现在「系统设置 → 隐私与安全性 → 屏幕录制」列表中
CGRequestScreenCaptureAccess()
// 后续 SCShareableContent 调用会触发首次授权弹窗
// 不要用 preflight 做守卫，直接让调用自然触发
```

### 9.3 隐私原则

- **音频不出本机**：全部识别在设备端完成（SpeechAnalyzer 与 MLX Whisper 均为端侧）
- **不落盘原始音频**：除非用户显式开启录制
- **字幕文本默认本地存储**，用户可清除
- 若未来引入云端识别引擎，必须**显式告知并单独授权**，不与本地路径混淆

## 十、实施路线

### 阶段一：音频层 + 平台字幕轨

**产出**：能捕获系统音频并落盘为 16 kHz 单声道；能取到平台字幕并渲染。
**验证**：捕获 10 分钟音频，无丢帧、无时钟漂移；平台字幕正确渲染。
**风险**：屏幕录制权限流程。**必须先验证 `.app` 包启动时权限归属正确。**

### 阶段二：预转写轨

**产出**：对本地文件，播放前完成预转写，字幕零延迟呈现。
**验证**：转写 30 分钟视频，与人工字幕比对 WER；确认领先量始终 ≥ 10 s。
**风险**：长音频的内存管理。large-v3 占 3 GB，需在转写完成后主动释放。

### 阶段三：实时流式轨

**产出**：对任意系统音频，草稿 + 精修双轨输出。
**验证**：直播场景下，端到端延迟 ≤ 3 s；草稿可见延迟 ≤ 500 ms。
**风险**：这是最复杂的一环。建议先在命令行原型验证 LocalAgreement-2 策略，再接入 UI。

### 阶段四：偏置层与修订协议

**产出**：术语词典生效；修订协议稳定无抖动。
**验证**：注入领域词典后，专有名词准确率有可量化提升（目标 B-WER 降低 ≥ 40%）。
**风险**：修订协议需要大量真实场景调参，阈值过松则抖动，过紧则不修正。

### 阶段五：反馈闭环与呈现完善

**产出**：用户纠错可累积；三种呈现形态完备；导出功能完整。
**验证**：连续使用一周后，个人词典能显著改善特定场景准确率。

## 十一、诚实的局限性说明

以下是本方案**无法解决**的问题，不应给用户造成"可以做到完全准确"的预期：

1. **专有名词与数字**：即使平台侧 AI 字幕也常出错。这是当前 ASR 技术的系统性短板，不是实现质量问题。
2. **DRM 保护内容**：系统层面禁止捕获，无技术手段绕过。
3. **多人重叠说话**：说话人分离（diarization）在实时场景下准确率显著下降。本方案未纳入 diarization，若需要应作为独立特性评估。
4. **强口音与低质量音频**：模型能力边界，无法通过架构优化突破。
5. **"确保准确"是不可达目标**：要做到真正准确，必须有人工校对环节。本方案的目标是**把机器输出的错误率降到用户可接受的水平**，并**提供便捷的纠错与导出通道**。

## 补记：方法学审查结论（2026-11-13 追加）

> 本文形成于 12 次网页检索之后，但**未做专利检索、未做备选方案穷举**。后续补做审查，结论见 `docs/LIVE-CAPTION-METHOD-REVIEW.md`。此处先记录需要修正的判断，避免本文被当作定稿使用。

**本文不是最优方案。** 补做检索后确认四处可改进：

1. **音源层漏项**：对非 DRM 网页视频，直接抽取 HLS/DASH 分片或独立音轨，在音质（无损、不混系统通知音）、可预取性（可提前拉取未来分片，天然满足"识别进度超前"）、权限（无需屏幕录制授权）三方面都优于系统音频回环。正确做法是四级降级：媒体流抽取 → 浏览器 tabCapture → 系统回环 → 虚拟声卡。
2. **模型层架构性疏漏**：本文把「非流式模型 Whisper + 滑动窗口重译」当作流式主选，属于绕路。原生流式架构（RNN-T / Conformer / Paraformer / Zipformer）首字延迟 70–140 ms，比批处理 Whisper 的 1,200–3,200 ms 低一个数量级。合理分工是原生流式模型负责快轨，Whisper large-v3 负责预转写与精修。
3. **策略层选型偏保守**：§5.2 写「AlignAtt 需替换推理栈，暂不采用」是**判断错误**。AlignAtt 是零训练的推理时策略，成本在于读取模型内部交叉注意力权重，不是重训。相对 wait-k 与 LocalAgreement，它平均高约 2 BLEU 且延迟低 0.5–0.8 秒（Interspeech 2023）。应列为首选，LA-2 作为无注意力权重时的降级。
4. **修订协议不够严谨**：§七的字符数/时间启发式阈值，可升级为「模型内部对齐覆盖率 + KV 缓存快照回退」，并引入专有名词豁免替换机制。

**还需收回第一轮的一处表述**：`accuracy = f(lookahead)` 仍不完整。训练侧手段（FastEmit、SelfAlign、ConstAlign）可在不增加前瞻的前提下降低预测延迟，更准确的刻画是 `accuracy = f(lookahead, alignment_policy, context_bias)`。

**公开专利文献提示的重复风险**：本文 §5.2 的快慢双引擎构思，与一组 2020-12-15 优先权、已在美国（US 11,532,312 B2、US 11,929,076 B2）与欧洲（EP 4 264 602 B1，2025-08-20 授权，Active）获授权、另有中国同族（CN 116635932 A）公开的专利文献高度重合。该组文献明确描述了「主引擎高准确率长前瞻 + 副引擎低延迟短前瞻并行 → 副结果先入 word list → 主结果合并替换」。其独立权利要求含特征级拼接限定，与本文的文本层合并不完全相同，但欧洲授权文本权利要求全文未取得，无法判断覆盖范围。若本功能对外分发，建议在实施前委托专业机构做一次正式检索并出具意见。此处仅为事实记录，不构成任何法律结论。

### A.3 三处最实质的技术补正

**① 音源层：媒体流分片抽取**

对非 DRM 网页视频，直接抽取 HLS/DASH 分片或独立音轨相比系统回环有三项优势：无损（平台原始编码，不混系统通知音、不做 48→16 kHz 重采样）、可预取（按时间窗提前拉取未来分片，天然满足「识别进度超前」）、免屏幕录制权限。开源项目「流声字幕」已实现三级降级：媒体抽取 → Chrome tabCapture → 系统声音捕获，并处理了拖动进度条重对齐、AudioWorklet 重采样、窗口重叠去重等细节。

反向证据：Chrome Live Caption 只监听经 Mojo 注册的 `AudioOutputDelegate` 输出流，B 站用 flv.js + WebAssembly + Web Audio API 混音会绕过该路径。说明「系统级捕获」通用但粗放，「音源级抽取」精确但需按站点适配——应并存且按可用性降级。

**② 模型层：原生流式 vs 离线模型包装**

| 方案 | 首字延迟 | 技术词汇 WER | 资源 |
|---|---|---|---|
| Sherpa-ONNX / Zipformer (RNN-T)，原生流式 | 70–140 ms | 11.8–15.5% | 1.2–2.0 GB |
| FunASR / Paraformer（非自回归），原生流式 | 百毫秒级 | 中文 CER 3.8% | 轻量 |
| Whisper large-v3（批处理） | 1,200–3,200 ms | 7.2–9.8% | 4.5–9.5 GB |
| 云端流式（低延迟档） | 180–320 ms | 6.5–8.9% | 客户端 <40 MB |

RTF 对比（5 分钟音频）：FunASR 流式 0.06（约 16 倍实时）> Paraformer-large 0.15 > Qwen3-ASR-1.7B 0.23 > Whisper-large-v3 0.31。

结论：上一版把"精度最高的模型"硬包装成流式是绕远路。正确分工是原生流式模型负责快轨，Whisper large-v3 负责预转写与精修。

**③ 策略层：AlignAtt 优于 LocalAgreement**

AlignAtt（Interspeech 2023）用 decoder 交叉注意力定位候选词对应音频帧，若落在缓冲区末尾「不可访问帧」窗口内则判语境不足、继续等待。相对 wait-k 与 LA：平均高约 2 BLEU，LAAL 延迟降低 0.5–0.8 秒，零训练零适配，单一参数 f 调节延迟/质量。局限是注意力弥散会导致决策不稳定。开源项目 SimulStreaming 已实现该策略并获 IWSLT 2025 同传冠军。

### A.4 从公开专利文献学到的三个改进

1. **类别词保护**：精修回填时，专有名词类词元应豁免替换。补上原设计修订协议的漏洞——高精度引擎在专有名词上未必更准。
2. **单模型双分支共享 encoder**：比跑两个独立模型省算力。对 M3 Max 意义有限，对内存受限设备关键。
3. **对齐覆盖率 + KV 快照回退**：把修订决策从外部启发式阈值提升到模型内部对齐信号 + 状态回滚。

| 6 | 部署 | 隐式全端侧 | 三形态可选，默认端侧但显式可切换 |
| 7 | 时间轴 | 绝对时间戳对齐 | 增加识别耗时补偿，字幕可提前展示 |

### A.7 需要收回的两处表述

1. 「实时与准确在物理上互斥」（第一轮回答）：不精确。更完整的刻画是 `accuracy = f(lookahead, alignment_policy, context_bias)`——训练侧手段（FastEmit / SelfAlign）可在不增加前瞻的前提下降低预测延迟。
2. 「AlignAtt 需替换推理栈，暂不采用」（§5.2）：判断错误。它是零训练的推理时策略，成本在于读取交叉注意力权重，不是重训。

### A.8 「最好」这个提法本身的问题

本节给出的是「2026-11 可检索公开信息下的方法空间更优位置」，不是绝对最优：

- 无单一最优解：音源可预取性、语言、是否联网、是否允许音频出本机、延迟预算——不同约束下最优解不同。
- benchmark 不可横比：各来源测试集、归一化规则、硬件都不同（LibriSpeech 朗读语音 vs AMI 远场会议，WER 可差 5 倍）。数字用于判断量级，不用于精确排序。
- 专利状态会变：部分 2026 年公开的申请仍在审查，权利要求可能被修改或驳回。
